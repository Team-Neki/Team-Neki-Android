# 릴리즈 버전과 출시 노트

릴리즈 PR에서 앱 버전과 스토어에 표시할 출시 노트를 함께 확정한다.

- `BuildConst.VERSION_NAME`: 이전 main보다 높은 버전(예: `1.4.6`).
- `release-notes/1.4.6/ko-KR.txt`: 한국어 사용자용 노트 1~500자. 다른 언어는 같은 폴더에 `en-US.txt`처럼 추가한다.
- PR 제목: `[release] v1.4.6`, base: `main`, 기본 head: `develop`, 라벨: `release`.

노트 예시:

```text
• 즐겨찾는 사진이 없어도 필터를 변경할 수 있어요.
• 포즈 목록의 필터와 정렬 동작을 개선했어요.
```

`main` 대상 PR은 버전 증가·제목 일치·한국어 노트 존재·CI를 검증한다. `release` 라벨이 있는 PR을 merge commit으로 머지하면 정확한 머지 소스가 프로덕션에 제출된다. Google에서 제출 상태를 확인한 뒤 `v1.4.6` 태그와 GitHub Release가 자동 생성된다. GitHub Release에는 이 노트와 PR 기반 개발 변경 내역이 함께 들어간다.

동일 버전·동일 git tree로 내부테스트에 게시된 후보가 있으면 같은 AAB와 versionCode를 프로덕션으로 승급한다. git tree가 다른 빌드나 출처 식별자가 없는 과거 내부 빌드는 재사용하지 않는다. 내부테스트 전에 버전·노트를 릴리즈할 소스에 포함해야 머지 후 같은 후보를 사용할 수 있다.

새 빌드의 버전 코드는 전체 Play 트랙 중 최댓값 다음 번호로 자동 계산한다. 재시도에서는 소스 SHA를 포함한 출시명으로 기존 제출을 식별하며, 같은 빌드를 중복 업로드하지 않는다. 기존 태그가 다른 소스를 가리키면 중단한다.

GitHub Release의 Play 상태는 약 15분 간격으로 갱신한다. 검토 중·게시 대기·거절·게시됨을 구분하며, 게시됨은 Google의 트랙 제공 상태다. 출시 비율과 중지 상세는 Play Console에서 확인한다. 정기 실행은 GitHub 사정에 따라 지연될 수 있다.

내부테스트는 `Deploy Play Store Internal Testing`을 명시적으로 수동 실행하며 정식 태그·Release를 생성하지 않는다. Firebase QA는 기존 debug APK 경로를 유지한다.

실제 배포 없이 검증하려면 `Verify Release Automation`을 실행한다. 서비스 계정은 상태 조회 외에 프로덕션 출시 권한도 있어야 하며, 실제 프로덕션 제출 경로는 다음 릴리즈에서 실행된다.

현재 Google 검토 중인 다른 프로덕션 릴리즈가 있거나 자동화 외의 Console 편집이 진행 중이면 먼저 해당 작업 상태를 정리한다. API 오류나 미제출 상태를 성공으로 표시하지 않는다.
